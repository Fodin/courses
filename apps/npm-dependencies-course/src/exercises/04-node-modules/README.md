# Уровень 4: Устройство node_modules

## Плоская структура: npm v3 и выше

До npm v2 зависимости устанавливались вложенно: каждый пакет получал собственную папку `node_modules` внутри себя. Это приводило к глубоким деревьям, дублированию и проблемам на Windows (ограничение длины пути).

Начиная с **npm v3** (2015) стандартом стала **плоская (flat) структура**: все пакеты поднимаются как можно выше — непосредственно в корневой `node_modules`. Это называется **hoisting**.

```
node_modules/
  react/
  react-dom/
  lodash/
  typescript/
```

Вместо бесконечной вложенности — один уровень для большинства пакетов.

## Hoisting — подъём зависимостей

Если два пакета требуют одну и ту же версию библиотеки, npm поднимает её в корень. Все потребители используют одну копию.

**Правило hoisting:** пакет поднимается в корень, если в корне ещё нет другой несовместимой версии того же пакета.

## Вложенные копии при конфликте версий

Если пакет A требует `lodash@4.x`, а пакет B требует `lodash@3.x`, и в корне уже стоит `lodash@4`, то `lodash@3` устанавливается **вложенно** — прямо внутри папки пакета B:

```
node_modules/
  lodash/          ← версия 4.x (hoisted)
  package-a/
  package-b/
    node_modules/
      lodash/      ← версия 3.x (вложенная копия)
```

Это единственный случай, когда появляется вложенность в npm v3+.

## Дедупликация

`npm dedupe` анализирует дерево и пытается поднять вложенные копии выше, если это не нарушает совместимость. Например, если оба пакета принимают `lodash@^4.0.0`, но одному досталась `4.1` а другому `4.2` — `dedupe` оставит только одну общую `4.2`.

## Что хранится в node_modules

- **Папки пакетов** — основной контент
- **`.bin/`** — симлинки (symbolic links) на исполняемые файлы пакетов. Когда вы пишете `npm run build` и в скрипте стоит `tsc`, npm ищет `./node_modules/.bin/tsc`
- **`.package-lock.json`** — скрытый файл, который Arborist использует для отслеживания состояния дерева (не путать с `package-lock.json` в корне проекта)
- **`.cache/`** — иногда встречается в зависимости от версии npm и настроек

## Фантомные зависимости (phantom dependencies)

Это серьёзная проблема плоской структуры. Раз все пакеты лежат в корневом `node_modules`, код вашего приложения может импортировать их **без явного объявления в `package.json`**.

```js
// В package.json нет "lodash", но lodash установлен транзитивно
const _ = require('lodash') // работает! но это фантомная зависимость
```

**Почему это опасно:** если прямая зависимость, которая тянула lodash, обновится или будет удалена — lodash исчезнет из `node_modules`, и ваш код сломается. Фантомные зависимости делают проект хрупким.

pnpm решает эту проблему через строгую изоляцию (уровень 15).

## ⚠️ Типичные ошибки

❌ Полагаться на транзитивно поднятые пакеты без добавления их в `dependencies`  
✅ Всегда явно указывать зависимости в `package.json`

❌ Коммитить `node_modules` в git  
✅ Держать `node_modules` в `.gitignore`, восстанавливать через `npm ci`

❌ Ожидать, что вложенных копий нет никогда  
✅ Знать: при конфликте версий вложенность неизбежна
