# Задание 12.3: Проектирование защиты API

## Цель

Реализовать интерактивный self-check по проектированию безопасности для трёх реальных сценариев. Студент изучает сценарий, пишет своё решение по четырём слоям (аутентификация, авторизация, шифрование, логирование), затем сравнивает с эталоном.

## Требования

1. Три карточки-сценария (кликабельные): публичный API с тарифами, внутренний API между микросервисами, банковский/финтех API
2. При выборе сценария — показать textarea для ответа студента с placeholder-подсказкой: опиши 4 слоя (аутентификация / авторизация / шифрование / логирование)
3. Кнопка «Показать эталонное решение» открывает панель с четырьмя блоками:
   - **Аутентификация** (схема: Basic/Bearer/JWT/mTLS, время жизни токена)
   - **Авторизация** (RBAC / ABAC / scopes, что чем ограничено)
   - **Шифрование** (TLS, mTLS, подпись тела при необходимости)
   - **Логирование** (что писать, что маскировать)
4. Активная карточка выделена рамкой (#6366f1), у неактивных — #e2e8f0
5. Ответы студента сохраняются при переключении между сценариями
6. Состояние «показан эталон» хранится отдельно для каждого сценария

## Чеклист

- [ ] Три карточки сценариев с иконкой, названием, описанием
- [ ] Клик по карточке раскрывает textarea для ответа
- [ ] Textarea сохраняет текст при переключении сценариев
- [ ] Кнопка «Показать эталонное решение» раскрывает панель из 4 блоков
- [ ] Панель эталона: аутентификация, авторизация, шифрование, логирование
- [ ] Состояние revealed хранится для каждого сценария отдельно

## Данные для сценариев (эталон)

### Сценарий 1: Публичный API для разработчиков
Тысячи внешних клиентов, сторонние приложения от имени пользователей.
- **Аутентификация:** OAuth 2.0, access-токен (JWT, exp ~15 мин) + refresh-токен.
- **Авторизация:** scopes (`orders:read`, `orders:write`) — каждому приложению минимально необходимый набор.
- **Шифрование:** только HTTPS + HSTS; секреты подписи в KMS.
- **Логирование:** request-id, client-id, статус; токены маскировать.

### Сценарий 2: Внутренний API между микросервисами
8 сервисов в приватной сети, нет конечного пользователя.
- **Аутентификация:** mTLS (взаимные сертификаты) или короткоживущие service-токены.
- **Авторизация:** RBAC по service-identity (какому сервису какой эндпоинт можно).
- **Шифрование:** mTLS закрывает и личность, и канал; service mesh.
- **Логирование:** сквозной trace-id для распределённой трассировки; без PII.

### Сценарий 3: Банковский / финтех API
Деньги, регуляторика (PCI DSS), высокая цена ошибки.
- **Аутентификация:** OAuth 2.0 + строгий MFA на чувствительные операции; короткий exp.
- **Авторизация:** ABAC (владелец счёта, лимиты, рабочие окна) поверх RBAC.
- **Шифрование:** TLS + подпись тела запроса (HMAC/`X-Signature`) для платежей; идемпотентность.
- **Логирование:** полный неизменяемый аудит транзакций; маскирование PAN/CVV/PII; ограниченный доступ и срок хранения.

## Как проверить себя

1. Для каждого сценария напиши своё решение по всем 4 слоям (хотя бы по пункту на слой).
2. Нажми «Показать эталон» и сравни.
3. Обрати внимание: чем выше цена ошибки, тем строже все четыре слоя — и тем больше ABAC, mTLS, подписи и аудита.

## Подсказки

- Состояние: `selected` (индекс сценария), `answers` (объект сценарий→текст), `revealed` (объект сценарий→bool).
- Эталон удобно хранить массивом объектов с полями `auth`, `authz`, `encryption`, `logging`.
- Сохранение ответа: `setAnswers(prev => ({ ...prev, [selected]: text }))`.
