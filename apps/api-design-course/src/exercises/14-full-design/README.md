# Проектирование реального API

## Чеклист API Design перед релизом

Хороший API — это не один удачный эндпоинт. Это система, в которой каждая деталь согласована с остальными. Вот 10 вопросов, которые нужно задать себе перед тем, как объявить API готовым.

### URL и ресурсы

- [ ] Все URL используют существительные во множественном числе (`/orders`, не `/getOrder`)
- [ ] Иерархия URL отражает отношения ресурсов (`/users/{id}/orders`)
- [ ] Единый стиль: нижний регистр + дефисы (`/reading-lists`)
- [ ] Нет дублирующих URL для одного ресурса

### HTTP-методы

- [ ] GET не изменяет состояние (безопасен)
- [ ] POST используется для создания и actions (не для обновлений)
- [ ] PUT/PATCH используются корректно (полная / частичная замена)
- [ ] DELETE — удаление, второй вызов тоже возвращает 2xx (идемпотентный)

### Статус-коды

- [ ] Нет 200 OK на ошибки
- [ ] 201 Created с заголовком Location после POST
- [ ] 204 No Content для DELETE и PATCH без тела
- [ ] 4xx — ошибки клиента, 5xx — ошибки сервера

### Данные

- [ ] Единый формат ошибок с `code`, `message`, `details`
- [ ] camelCase для всех JSON-полей
- [ ] Даты в ISO 8601 с UTC: `"2024-01-15T10:30:00Z"`
- [ ] Деньги: `{ "amount": 850.00, "currency": "RUB" }`, не строки

### Пагинация и фильтрация

- [ ] Все списочные эндпоинты имеют пагинацию
- [ ] Разумный default limit (20) и максимум (100)
- [ ] Фильтрация через query-параметры
- [ ] `meta` в ответе: total, page, hasNext

## Процесс API Design Review

Ревью API — это не «посмотреть, нет ли опечаток». Это системная проверка по нескольким измерениям:

**1. Консистентность** — все эндпоинты соответствуют одному стилю. Если в одном месте пишешь `createdAt`, нельзя в другом писать `created_at`.

**2. Предсказуемость** — разработчик может угадать URL нового эндпоинта, зная шаблон. `/users/{id}/orders` → `/users/{id}/reviews` — логично.

**3. Полнота** — покрыты все статус-коды, все edge cases задокументированы.

**4. Безопасность** — нет утечки внутренних данных в ответах, auth правильно расставлен.
