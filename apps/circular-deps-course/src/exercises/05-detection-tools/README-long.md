# Обнаружение циклов: madge и dependency-cruiser (подробно)

## 🎯 Проблема

Циклическая зависимость — это баг, который не проявляется на этапе компиляции. `tsc` спокойно скомпилирует файлы `a.ts` и `b.ts`, импортирующие друг друга: с точки зрения типов всё сходится, а то, что в рантайме один из модулей на момент своей инициализации получит `undefined` вместо экспорта другого — компилятору неважно (подробнее — уровень 2). IDE тоже не гарантия: подсветка непостоянна, зависит от настроек, и никто не проверяет весь граф руками перед каждым коммитом.

Нужен инструмент, который:

1. Строит граф зависимостей всего проекта.
2. Ищет в этом графе циклы (сильно связные компоненты).
3. Печатает их в понятном виде или падает с ошибкой в CI.

Два самых распространённых — **madge** и **dependency-cruiser**.

## 💡 madge — быстрый поиск циклов

### Установка и базовый запуск

```bash
npm install --save-dev madge
# или разово через npx, без установки
npx madge --circular --extensions ts,tsx src
```

Флаг `--circular` включает режим поиска циклов (по умолчанию madge просто строит граф). `--extensions ts,tsx` нужен, чтобы madge резолвил TypeScript/TSX-файлы (по умолчанию он ориентирован на `.js`).

### Как читать вывод

```
✖ Found 2 circular dependencies!

1) src/entities/user/model/user.ts > src/entities/order/model/order.ts > src/entities/user/model/user.ts
2) src/features/cart/index.ts > src/entities/cart/index.ts > src/features/cart/index.ts
```

Каждая строка — это один найденный цикл, записанный как путь `A > B > ... > A`:

- Порядок читается **слева направо**: `A` импортирует `B`, `B` импортирует `C`, и так далее, пока цепочка не возвращается к `A`.
- Последний элемент строки всегда совпадает с первым — это и есть точка замыкания цикла.
- Если в проекте несколько независимых циклов, madge перечисляет их все по порядку под заголовком `Found N circular dependencies!`.

Чтобы найти «место разрыва» (какой импорт убрать/заменить), обычно смотрят на **самое слабое звено** — импорт, который используется только ради одного типа или константы; такой легче всего вынести в отдельный модуль (приём разбирается в уровне 7).

### Полезные флаги

```bash
# Только предупреждение в консоли, без падения процесса с ненулевым кодом
npx madge --circular --warning src

# Явно завершить процесс с ошибкой, если циклы найдены — удобно для CI
npx madge --circular src; echo $?   # ненулевой код при находке циклов

# Сгенерировать визуальный граф всего проекта (нужен установленный graphviz)
npx madge --image graph.svg src

# Найти "сироты" — файлы, на которые никто не ссылается
npx madge --orphans src

# Исключить директории/файлы по regexp из анализа
npx madge --exclude '^src/generated' --circular src
```

`--image` требует установленного [Graphviz](https://graphviz.org/) в системе (`dot` в PATH) — без него madge не сможет отрендерить картинку, хотя сам граф зависимостей построит.

### Когда madge удобен

- Быстрый разовый прогон «есть ли у нас вообще циклы?».
- Визуализация всего графа модулей для онбординга новых разработчиков.
- Лёгкая интеграция в `npm script` без сложной конфигурации.

## 💡 dependency-cruiser — архитектурный линтер

`dependency-cruiser` устроен иначе: это не просто «найди циклы», а полноценная система правил про то, **что кому разрешено импортировать**. Обнаружение циклов — лишь одно из встроенных правил.

### Установка и инициализация конфига

```bash
npm install --save-dev dependency-cruiser
npx depcruise --init
```

Команда `--init` создаёт `.dependency-cruiser.cjs` с набором правил «из коробки», включая `no-circular`.

### Правило no-circular

```js
// .dependency-cruiser.cjs
module.exports = {
  forbidden: [
    {
      name: 'no-circular',
      severity: 'error',
      comment:
        'Циклическая зависимость. Разорвите её: вынесите общее в отдельный модуль, ' +
        'используйте инверсию зависимостей или dynamic import.',
      from: {},
      to: { circular: true },
    },
  ],
  options: {
    tsPreCompilationDeps: true,
  },
}
```

Ключевые поля:

- `severity: 'error'` — при находке цикла инструмент завершится с ненулевым кодом (удобно для CI-гейта); можно понизить до `'warn'` на переходный период при разборе legacy-кода.
- `to: { circular: true }` — сама проверка на цикличность; движок дерева зависимостей внутри `dependency-cruiser` резолвит это автоматически.
- `tsPreCompilationDeps: true` — учитывать импорты по TypeScript-семантике до компиляции (важно для `import type` и path-алиасов).

### Запуск

```bash
npx depcruise src --config .dependency-cruiser.cjs

# Человекочитаемый отчёт с ошибками и предупреждениями
npx depcruise src --config .dependency-cruiser.cjs --output-type err-long

# Визуальный граф всего проекта в формате dot → svg
npx depcruise src --config .dependency-cruiser.cjs --output-type dot | dot -T svg > graph.svg
```

Вывод при находке цикла с `--output-type err-long` выглядит примерно так:

```
error no-circular: src/entities/user/model/user.ts →
  src/entities/order/model/order.ts →
  src/entities/user/model/user.ts

✖ 1 dependency violations (1 errors, 0 warnings). 3 modules cruised.
```

Формат похож на madge, но явно помечен уровнем severity (`error`/`warn`) и именем нарушенного правила — это удобно, когда правил в конфиге много и нужно быстро понять, какое именно сработало.

### Когда dependency-cruiser удобен

- Нужны не только циклы, но и другие архитектурные правила: запрет импортов из `node_modules` напрямую, границы между слоями FSD (см. уровни 8–11), запрет циклов только внутри определённой директории.
- Проект уже большой, и нужен единый источник правды про архитектуру, зафиксированный в конфиге и проверяемый в CI.
- Нужен кастомный отчёт (JSON, HTML, dot) для интеграции с другими инструментами.

## 🔥 Почему tsc и IDE не решают эту задачу

`tsc` анализирует типы и синтаксис, но не строит граф модулей ради поиска циклов — с точки зрения системы типов цикл `a.ts ↔ b.ts` абсолютно валиден, если типы сходятся. Единственное исключение — `import type`-only циклы, которые в принципе безопасны в рантайме (уровень 3), но `tsc` их не проверяет специально, они просто не создают рантайм-проблем.

IDE может подсвечивать «неиспользуемый импорт» или ошибку резолва пути, но не имеет встроенного правила «этот импорт участвует в цикле» — такую проверку нужно явно подключать через плагин (обычно как раз ESLint-правило, уровень 6) или запускать отдельно.

## 📌 madge vs dependency-cruiser — сравнение

|                                 | madge                                       | dependency-cruiser                                                  |
| ------------------------------- | ------------------------------------------- | ------------------------------------------------------------------- |
| Установка/конфиг                | Не нужен, работает из коробки               | Требует `.dependency-cruiser.cjs`                                   |
| Скорость первого запуска        | Быстрее                                     | Чуть медленнее из-за парсинга правил                                |
| Поиск циклов                    | Основная функция                            | Одно из многих правил                                               |
| Кастомные архитектурные правила | Нет                                         | Да, гибкая система `forbidden`/`allowed`                            |
| Визуализация графа              | `--image` (через Graphviz)                  | `--output-type dot/svg` (через Graphviz)                            |
| Подходит для                    | Разовой диагностики, малых/средних проектов | Долгосрочного гейта в CI, больших проектов с явными границами слоёв |

**Практическое правило:** если задача — «просто найти циклы и глянуть на граф», хватит madge. Если нужно зафиксировать архитектурные границы (например, границы FSD-слоёв из уровня 8) и держать их под контролем в CI годами — dependency-cruiser.

## ⚠️ Частые ошибки новичков

❌ Запускать madge без `--extensions ts,tsx` в TS-проекте и удивляться, что циклы «не находятся»:

```bash
npx madge --circular src
```

Почему проблема: по умолчанию madge настроен на резолв `.js`-файлов; `.ts`/`.tsx` могут не подхватиться, и часть графа окажется невидимой.

✅ Явно указать расширения:

```bash
npx madge --circular --extensions ts,tsx src
```

---

❌ Считать, что «раз `tsc` собрался без ошибок — циклов нет»:

```ts
// a.ts
import { b } from './b'
export const a = 1
// b.ts
import { a } from './a'
export const b = 2
```

Почему проблема: этот код действительно скомпилируется без единой ошибки TypeScript, но в рантайме порядок инициализации может привести к `undefined` (см. уровень 2). Компилятор не проверяет цикличность графа модулей.

✅ Добавить отдельный шаг обнаружения циклов (madge/dependency-cruiser) в pre-commit или CI, не полагаясь на `tsc`.

---

❌ Держать правило `no-circular` со `severity: 'warn'` бессрочно, «чтобы не мешало»:

```js
{ name: 'no-circular', severity: 'warn', to: { circular: true } }
```

Почему проблема: предупреждения копятся и перестают замечаться (эффект «баннерной слепоты»), новые циклы просачиваются в проект незамеченными.

✅ Использовать `warn` только как временный этап при расчистке legacy-циклов, с явным планом перехода на `error` (уровень 13 — CI prevention).

## ✅ Лучшие практики

1. Запускайте поиск циклов **в CI**, а не только вручную — тогда цикл не попадёт в main.
2. Используйте `madge --circular` для быстрой локальной проверки во время разработки и `dependency-cruiser` с `no-circular: error` как гейт в pipeline.
3. Исключайте из анализа сгенерированный код (`--exclude`) — иначе будете чинить циклы в файлах, которые перезапишутся при следующей генерации.
4. При находке цикла сначала прочитайте цепочку целиком (`A > B > C > A`), а не первый попавшийся импорт — часто разрыв логичнее делать не в том модуле, где обнаружили ошибку, а в самом «тонком» звене цепочки.
5. Для больших монорепозиториев комбинируйте оба инструмента: madge — для быстрой диагностики пакета, dependency-cruiser — для проверки границ между пакетами (см. уровень 12).
