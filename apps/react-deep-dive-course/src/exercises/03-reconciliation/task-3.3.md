# Задание 3.3: Key Reset vs useEffect (YMNAE)

## Цель

Сравнить два подхода к сбросу state при смене "текущего пользователя": через `useEffect` (антипаттерн) и через `key` (правильный паттерн из "You Might Not Need an Effect"). Счётчик рендеров покажет разницу в количестве лишних рендеров.

## Требования

1. Создать список из 3 пользователей с кнопками переключения: "Alice", "Bob", "Charlie".
2. Реализовать компонент `ProfileEditorV1` (антипаттерн):
   - State: `name`, `bio`
   - `useEffect(() => { setName(''); setBio('') }, [userId])` для сброса
   - Счётчик рендеров через `useRef`
3. Реализовать компонент `ProfileEditorV2` (правильный паттерн):
   - Тот же state: `name`, `bio`
   - Никакого useEffect
   - Рендерится через `<ProfileEditorV2 key={userId} userId={userId} />`
   - Счётчик рендеров через `useRef`
4. Показать оба варианта рядом. При переключении пользователя — оба должны отобразить одинаковый результат (пустые поля), но количество рендеров будет отличаться.
5. Добавить пояснение: сколько рендеров происходит в каждом варианте при переключении и почему.

## Чеклист

- [ ] Список из 3 пользователей с кнопками переключения
- [ ] ProfileEditorV1 с useEffect для сброса state
- [ ] ProfileEditorV2 с key={userId} для пересоздания
- [ ] Счётчик рендеров у каждого варианта (через useRef, не useState)
- [ ] При переключении пользователя оба варианта показывают пустые поля
- [ ] V1 делает больше рендеров (видно по счётчику)
- [ ] Пояснение разницы: почему V2 лучше

## Как проверить себя

1. Открой оба варианта. Начальные счётчики рендеров: по 1 (первый mount).
2. Переключись на другого пользователя.
3. V1: счётчик вырастет на 2-3 (рендер с новым userId + рендеры от setName/setBio).
4. V2: счётчик сбросится в 1 (компонент пересоздан с нуля).
5. Введи что-нибудь в поля V1 и переключись — заметь мгновение, когда поля ещё показывают старые данные.
6. В V2 такого "мерцания" нет — компонент всегда начинает с чистого листа.

## Зачем это важно

Паттерн из официальной документации React "You Might Not Need an Effect":

> If you want to reset some state when a prop changes, consider using a `key` instead.

Это не просто оптимизация — это семантически правильная модель. Смена userId означает "это другой пользователь", а не "обновился prop". key выражает это намерение явно.
