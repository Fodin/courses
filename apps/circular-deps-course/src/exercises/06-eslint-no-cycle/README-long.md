# ESLint import/no-cycle (подробно)

## 🎯 Проблема

`madge` и `dependency-cruiser` (уровень 5) находят циклы уже готового кода — обычно во время отдельного CI-шага или ручного прогона. Это работает, но обратная связь приходит поздно: разработчик уже написал фичу, закоммитил, дождался пайплайна — и только тогда узнаёт о цикле.

Хочется получать сигнал **в момент написания кода**, прямо в редакторе, тем же инструментом, что уже подсвечивает неиспользуемые переменные и неправильный порядок импортов — ESLint.

## 💡 import/no-cycle vs import-x/no-cycle

Исторически правило `no-cycle` жило в пакете `eslint-plugin-import`. Этот плагин много лет не успевал за новым ESLint (flat config, ESM) и в современных проектах его чаще заменяют форком **eslint-plugin-import-x**, который поддерживает то же самое правило под именем `import-x/no-cycle` с идентичной логикой и опциями. Дальше в примерах используется `import-x`, но всё сказанное применимо и к классическому `import/no-cycle`.

### Установка

```bash
npm install --save-dev eslint-plugin-import-x
```

### Подключение в flat config

```js
// eslint.config.js
import importX from 'eslint-plugin-import-x'

export default [
  {
    plugins: { 'import-x': importX },
    rules: {
      'import-x/no-cycle': [
        'error',
        {
          maxDepth: 10,
          ignoreExternal: true,
        },
      ],
    },
  },
]
```

Правило требует резолвер для алиасов путей (например, `eslint-import-resolver-typescript`), если в проекте используются `tsconfig`-пути (`@/entities/...`) — иначе часть импортов не срезолвится и цикл через алиас останется незамеченным.

## 🔥 Как читать сообщение об ошибке

Базовый вариант, когда цикл найден напрямую в текущем файле:

```
error  Dependency cycle detected  import-x/no-cycle
```

Более информативный вариант, когда цикл проходит через промежуточные модули:

```
src/entities/user/model/user.ts
  3:1  error  Dependency cycle via ./order.ts:5  import-x/no-cycle
```

Разбор по частям:

- **`3:1`** — строка и колонка импорта в текущем файле (`user.ts`), с которого ESLint начал обход и на котором сработало правило.
- **`Dependency cycle via ./order.ts:5`** — путь, ЧЕРЕЗ который замкнулся цикл: `order.ts`, а конкретно строка `5` в нём — тот импорт, который в итоге приводит обратно к `user.ts`.
- **`import-x/no-cycle`** — имя правила, полезно при большом количестве правил в конфиге, чтобы понять, куда смотреть за документацией/опциями.

Чтобы восстановить полный путь цикла, нужно открыть указанный файл (`order.ts`) на указанной строке (`5`) и посмотреть, что он импортирует — обычно это снова `user.ts` или модуль, который дальше приводит к нему.

**Практика поиска места разрыва:** цикл почти всегда можно разорвать не в том файле, где сработала ошибка, а в одном из промежуточных — там, где импортируется что-то одно узкое (тип, константа, одна функция). Такой импорт легче всего вынести в третий модуль (уровень 7) или заменить на `import type`.

## 📌 Опции правила

| Опция                                | Назначение                                                                        | Когда менять                                                                                                                                                   |
| ------------------------------------ | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `maxDepth`                           | Максимальная глубина обхода графа импортов при поиске цикла                       | Уменьшить на очень больших проектах ради скорости линта; ценой пропуска длинных циклов                                                                         |
| `ignoreExternal`                     | Не учитывать импорты из `node_modules` при поиске циклов                          | Включать почти всегда — циклы внутри чужих пакетов не наша забота                                                                                              |
| `allowUnsafeDynamicCyclicDependency` | Не считать цикл нарушением, если он разорван через `import()` (dynamic import)    | Включать точечно, когда команда сознательно использует dynamic import как приём разрыва (уровень 7) — иначе линтер будет ругаться даже на «безопасный» вариант |
| `disableScc`                         | Отключить оптимизацию поиска через выделение сильно связных компонент (SCC) графа | Обычно не трогать; может понадобиться при отладке самого правила на нетипичном графе                                                                           |

### maxDepth — компромисс скорость/полнота

```js
'import-x/no-cycle': ['error', { maxDepth: 10 }]
```

Правило обходит граф импортов рекурсивно от каждого файла. На больших монорепозиториях с тысячами модулей полный обход может заметно замедлить линт (особенно в watch-режиме IDE). `maxDepth` ограничивает, на сколько «шагов» вглубь идёт обход:

- Маленькое значение (`3`–`5`) — линт быстрее, но длинные циклы (через много промежуточных модулей) можно не заметить.
- Большое значение или значение по умолчанию (`Infinity` в некоторых версиях) — находит все циклы, но может ощутимо тормозить на очень больших графах.

На практике для большинства проектов среднего размера достаточно значения `10`; для очень крупных монорепозиториев стоит замерить время линта и подбирать эмпирически, комбинируя с `dependency-cruiser` в CI (который не имеет таких ограничений по глубине) как «дополнительной сетью безопасности».

### allowUnsafeDynamicCyclicDependency и dynamic import

```js
// a.ts
export async function loadB() {
  const { b } = await import('./b')
  return b
}
```

Формально `a.ts` и `b.ts` всё ещё образуют цикл в графе зависимостей, но динамический импорт откладывает загрузку `b.ts` до момента вызова функции — на момент инициализации модуля `a.ts` цикл не «взрывается» так, как это было бы со статическим импортом (уровень 1–2). Опция `allowUnsafeDynamicCyclicDependency: true` говорит правилу не считать такие цепочки нарушением. Название содержит слово «unsafe» неспроста: dynamic import действительно снимает проблему инициализации, но не убирает архитектурную связанность между модулями — используйте её осознанно, а не как способ заглушить линтер.

## ⚠️ Частые ошибки новичков

❌ Увидеть ошибку линта и просто обернуть весь файл в `// eslint-disable-next-line import-x/no-cycle`:

```ts
// eslint-disable-next-line import-x/no-cycle
import { Order } from './order'
```

Почему проблема: цикл никуда не делся, просто линт замолчал. Рантайм-риски (TDZ, undefined на инициализации, уровень 2) остаются, а следующий разработчик даже не узнает о проблеме.

✅ Разобраться в причине цикла и применить один из приёмов уровня 7 (вынос общего в третий модуль, инверсия зависимостей, `import type`, dynamic import с явным `allowUnsafeDynamicCyclicDependency`).

---

❌ Включить правило без резолвера путей в проекте с алиасами (`@/entities/...`):

```js
rules: { 'import-x/no-cycle': 'error' }
// но settings['import-x/resolver'] не настроен
```

Почему проблема: ESLint не сможет сопоставить алиас с реальным файлом, часть импортов «выпадет» из графа, и цикл через алиас останется незамеченным — ложное чувство безопасности.

✅ Подключить резолвер (`eslint-import-resolver-typescript`) и указать его в `settings`.

---

❌ Ставить `maxDepth: 2` «для скорости» на всём монорепозитории:

```js
'import-x/no-cycle': ['error', { maxDepth: 2 }]
```

Почему проблема: большинство реальных циклов проходят через 3+ модуля (barrel-файлы часто добавляют лишний уровень косвенности), и с такой глубиной линтер их просто не увидит.

✅ Подбирать `maxDepth` эмпирически (замерить время линта на CI), и дублировать проверку через `dependency-cruiser` без ограничения глубины как финальный гейт.

## ✅ Лучшие практики

1. Включайте `import-x/no-cycle`/`import/no-cycle` как `error`, а не `warn` — иначе предупреждения тонут в общем шуме линтера.
2. Держите `ignoreExternal: true` почти всегда — вы не контролируете граф импортов внутри `node_modules`.
3. Комбинируйте ESLint-правило (быстрая обратная связь при разработке) с `dependency-cruiser`/`madge` в CI (полная проверка без ограничения по глубине) — это разные рубежи защиты, не взаимозаменяемые.
4. Используйте `allowUnsafeDynamicCyclicDependency` точечно и осознанно, а не как способ обойти правило — dynamic import решает проблему инициализации, но не убирает связанность.
5. При получении сообщения `Dependency cycle via ...` начинайте разбор с указанного промежуточного файла и строки — обычно именно там находится самый простой для разрыва импорт.
