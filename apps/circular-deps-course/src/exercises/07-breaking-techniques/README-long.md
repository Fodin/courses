# Каталог приёмов разрыва циклов (подробно)

## 🎯 Проблема

Цикл найден (уровни 5–6). Дальше встаёт вопрос: **как именно** его разорвать? «Просто убрать импорт» не всегда возможно — код действительно нуждается в данных из другого модуля. Нужен каталог проверенных приёмов, каждый со своей ситуацией применения, чтобы не изобретать решение с нуля каждый раз.

## 💡 Приём 1 — Третий модуль (самый частый)

**Симптом:** два модуля используют одну и ту же сущность (тип, константу, утилитарную функцию), и импортируют её друг у друга, хотя логически она не принадлежит ни одному из них.

```ts
// ❌ Было: цикл
// user.ts
import { Order } from './order'
export interface User {
  orders: Order[]
}

// order.ts
import { User } from './user'
export interface Order {
  owner: User
}
```

```ts
// ✅ Стало: общее вынесено в третий, нижележащий модуль
// types.ts
export interface User {
  orders: Order[]
}
export interface Order {
  owner: User
}

// user.ts
import type { User } from './types'
export function createUser(): User {
  /* ... */
}

// order.ts
import type { Order } from './types'
export function createOrder(): Order {
  /* ... */
}
```

**Почему работает:** цикл существует потому, что граф зависимостей содержит путь A→B→A. Если оба модуля вместо друг друга начинают зависеть от третьего, независимого от них файла, стрелки идут только «вниз» (A→C, B→C), а обратного пути B→A/A→B больше нет — граф становится ациклическим (DAG).

## 💡 Приём 2 — Инверсия зависимостей (DIP)

**Симптом:** модуль верхнего уровня (бизнес-логика) напрямую импортирует модуль нижнего уровня (конкретную реализацию), а тот в какой-то момент тоже начинает нуждаться в чём-то из верхнего.

```ts
// ❌ Было: сервис импортирует конкретный логгер, логгер импортирует тип из сервиса
// order-service.ts
import { FileLogger } from './file-logger'
export class OrderService {
  constructor(private logger: FileLogger) {}
}

// file-logger.ts
import { OrderService } from './order-service'
export class FileLogger {
  log(ctx: OrderService) {
    /* ... */
  }
}
```

```ts
// ✅ Стало: верхний модуль определяет интерфейс (порт), нижний его реализует
// logger.ts (порт — принадлежит верхнему слою)
export interface Logger {
  log(message: string): void
}

// order-service.ts
import type { Logger } from './logger'
export class OrderService {
  constructor(private logger: Logger) {}
}

// file-logger.ts (реализация — зависит от абстракции, а не наоборот)
import type { Logger } from './logger'
export class FileLogger implements Logger {
  log(message: string) {
    /* ... */
  }
}
```

**Суть DIP:** «зависеть нужно от абстракций, а не от деталей». Раньше стрелка шла и туда, и обратно; после инверсии обе стороны зависят от общего интерфейса, но не друг от друга напрямую — тот же принцип, что и в приёме с третьим модулем, только абстракция здесь — контракт поведения, а не структура данных.

## 💡 Приём 3 — Внедрение зависимости

**Симптом:** функции/классу нужен доступ к чему-то из «соседнего» модуля, но этот доступ нужен только в момент вызова, а не при загрузке модуля.

```ts
// ❌ Было: cart.ts напрямую импортирует applyDiscount из pricing.ts,
// а pricing.ts импортирует тип корзины из cart.ts
// cart.ts
import { applyDiscount } from './pricing'
export function checkout(items: Item[]) {
  return applyDiscount(items)
}

// pricing.ts
import type { Item } from './cart'
export function applyDiscount(items: Item[]) {
  /* ... */
}
```

```ts
// ✅ Стало: pricing-функция передаётся параметром, cart.ts больше не импортирует pricing.ts
// cart.ts — не знает о pricing.ts вообще
export function checkout(items: Item[], applyDiscount: (items: Item[]) => Item[]) {
  return applyDiscount(items)
}

// вызывающий код (например, entry point) связывает оба модуля
import { checkout } from './cart'
import { applyDiscount } from './pricing'
checkout(items, applyDiscount)
```

**Отличие от третьего модуля:** здесь не выносится общая сущность — вместо этого разрывается сама связь импорта, а связывание переносится на уровень выше (композиция происходит там, где оба модуля и так уже видны).

## 💡 Приём 4 — События / mediator / шина

**Симптом:** A должен «оповестить» B о чём-то, но при этом B тоже должен уметь оповещать A — прямой двусторонний вызов неизбежно создаёт цикл.

```ts
// ❌ Было: cart.ts вызывает notifications.ts напрямую, notifications.ts импортирует тип из cart.ts для подписки
// cart.ts
import { notify } from './notifications'
export function addItem(item: Item) {
  notify('item-added', item)
}

// notifications.ts
import type { Item } from './cart'
export function notify(event: string, payload: Item) {
  /* ... */
}
```

```ts
// ✅ Стало: оба модуля общаются через независимую шину событий
// event-bus.ts — не знает ни о cart, ни о notifications
type Handler = (payload: unknown) => void
const handlers = new Map<string, Handler[]>()
export function emit(event: string, payload: unknown) {
  handlers.get(event)?.forEach(h => h(payload))
}
export function on(event: string, handler: Handler) {
  handlers.set(event, [...(handlers.get(event) ?? []), handler])
}

// cart.ts
import { emit } from './event-bus'
export function addItem(item: Item) {
  emit('item-added', item)
}

// notifications.ts
import { on } from './event-bus'
on('item-added', payload => {
  /* ... */
})
```

**Когда уместно:** когда логически связь «многие ко многим» или обратная связь нужна не всегда — шина событий развязывает модули полностью, но ценой того, что поток данных становится неявным (сложнее трассировать «кто на что подписан»).

## 💡 Приём 5 — Dynamic import()

**Симптом:** модуль B нужен модулю A редко, не на этапе инициализации, а по какому-то условию или действию пользователя.

```ts
// ❌ Было: статический импорт создаёт цикл, срабатывающий сразу при загрузке a.ts
// a.ts
import { featureB } from './b'
export function run() {
  featureB()
}
```

```ts
// ✅ Стало: импорт откладывается до вызова
// a.ts
export async function run() {
  const { featureB } = await import('./b')
  featureB()
}
```

**Цена приёма:** функция становится асинхронной (нужен `await`/промис по всей цепочке вызовов), а сборщик обычно выносит модуль `b.ts` в отдельный чанк — это может быть желательно (ленивая загрузка тяжёлого функционала) или нежелательно (лишняя сложность ради разрыва простого цикла). Уместен, когда связь между модулями действительно редкая/опциональная, а не просто «неудобно вынести в третий модуль».

## 💡 Приём 6 — Слияние модулей

**Симптом:** два файла настолько тесно связаны, что фактически представляют одну сущность, искусственно разбитую на части (например, «класс» и «его приватные хелперы», зависящие друг от друга в обе стороны).

```ts
// ❌ Было: helpers.ts и validator.ts взаимно импортируют друг друга
// validator.ts
import { normalize } from './helpers'
export function validate(v: string) {
  return normalize(v).length > 0
}

// helpers.ts
import { validate } from './validator'
export function normalize(v: string) {
  return v.trim()
}
export function isValidOrThrow(v: string) {
  if (!validate(v)) throw new Error('invalid')
}
```

```ts
// ✅ Стало: объединены в один модуль, цикл исчезает вместе с искусственной границей
// validation.ts
export function normalize(v: string) {
  return v.trim()
}
export function validate(v: string) {
  return normalize(v).length > 0
}
export function isValidOrThrow(v: string) {
  if (!validate(v)) throw new Error('invalid')
}
```

**Когда уместно:** когда разделение на файлы не отражает реальных архитектурных границ, а является лишь искусственным дроблением «для порядка». Если границы осмысленные (например, слой FSD, уровень 8) — сливать не стоит, лучше применить один из предыдущих приёмов.

## 💡 Приём 7 — import type

Подробно разобран в уровне 3. Если цикл существует только ради типа (интерфейса, generic-параметра), а не ради значения (функции, класса, константы), достаточно заменить обычный импорт на `import type` — TypeScript сотрёт такой импорт при компиляции, и в скомпилированном JS цикла попросту не будет.

```ts
// ✅ Type-only цикл безопасен
// a.ts
import type { BType } from './b'
export interface AType {
  b: BType
}

// b.ts
import type { AType } from './a'
export interface BType {
  a: AType
}
```

Это не «настоящий» разрыв графа модулей до компиляции, но он безопасен, потому что рантайм-цикла не возникает вообще (см. уровень 3 про TDZ и стирание типов).

## ⚠️ Частые ошибки новичков

❌ Хвататься за dynamic import как за универсальное решение любого цикла:

```ts
// Цикл был из-за общего типа, а не из-за редкого вызова
export async function createOrder() {
  const { User } = await import('./user')
  // ...
}
```

Почему проблема: если связь на самом деле про типы или про общую сущность, dynamic import добавляет ненужную асинхронность и лишний чанк там, где хватило бы `import type` или третьего модуля.

✅ Сначала определить симптом (таблица ниже), затем выбирать приём — не наоборот.

---

❌ Сливать модули только потому, что «так проще убрать ошибку линтера»:

```ts
// Объединили user.ts и order.ts в один файл user-order.ts,
// хотя это два разных доменных понятия
```

Почему проблема: слияние стирает осмысленную архитектурную границу (например, между сущностями в FSD), создавая God-объект вместо решения реальной проблемы связанности.

✅ Слияние уместно только когда границы между файлами действительно искусственны, а не когда это просто самый быстрый способ погасить ошибку.

---

❌ Применять инверсию зависимостей (DIP) там, где достаточно вынести общий тип в третий модуль:

```ts
// Ради одного простого DTO-интерфейса городится интерфейс + две реализации
```

Почему проблема: DIP — более тяжеловесный приём (лишний уровень абстракции), оправданный, когда реально нужна подмена реализации (тестовые дублёры, разные окружения). Для простого общего типа это избыточно.

✅ Для «просто общей структуры данных» — третий модуль; для «поведения, которое надо инвертировать/подменять» — DIP.

## ✅ Симптом → приём (шпаргалка)

| Симптом                                              | Рекомендуемый приём         |
| ---------------------------------------------------- | --------------------------- |
| Два модуля используют общий тип/константу/утилиту    | Третий модуль               |
| Верхний слой знает о нижнем, а нижний — о верхнем    | Инверсия зависимостей (DIP) |
| Нужен доступ только в момент вызова, не при загрузке | Внедрение зависимости       |
| Связь «многие ко многим» / реакция на событие        | События / mediator          |
| Модуль нужен редко, опционально, можно отложить      | Dynamic import              |
| Разделение на файлы искусственно                     | Слияние модулей             |
| Цикл существует только ради типов                    | import type                 |

## ✅ Лучшие практики

1. Сначала определите симптом цикла (что именно является причиной — общий тип, поведение, событие), а не хватайтесь за первый попавшийся приём.
2. Предпочитайте «третий модуль» и `import type` как самые дешёвые и наименее инвазивные приёмы — начинайте с них.
3. DIP и события оправданы, когда реально нужна гибкость (подмена реализации, множественные подписчики) — не применяйте их «на всякий случай».
4. Dynamic import — осознанный компромисс (асинхронность, доп. чанк), а не способ спрятать архитектурную проблему.
5. После разрыва цикла обязательно перепроверьте результат тем же инструментом, которым он был найден (madge/dependency-cruiser/ESLint из уровней 5–6), чтобы убедиться, что цикл не переместился, а действительно исчез.

## 🧪 Практика

Теории мало — три приёма из этого каталога (инверсия зависимости, dynamic import, третий модуль) нужно отработать руками на 9 LAB-заданиях (7.1–7.9): в каждом дан реальный код с циклом, и его нужно отредактировать в песочнице так, чтобы граф импортов стал ациклическим именно тем приёмом, который требуется условием задания.
