# Уровень 6: Версионирование API

## Зачем версионировать API?

API — это контракт между сервером и клиентами. Когда вы меняете этот контракт, вы рискуете сломать
все приложения, которые на него полагаются. Версионирование позволяет вводить изменения постепенно,
не ломая существующих клиентов.

## Breaking vs Non-breaking changes

**Non-breaking (безопасные изменения):**
- Добавление нового поля в ответ
- Добавление нового необязательного параметра запроса
- Добавление нового endpoint

**Breaking (ломающие изменения):**
- Удаление поля из ответа
- Изменение типа поля (`string` → `number`)
- Переименование поля
- Изменение семантики существующего поля
- Удаление endpoint

## Три стратегии версионирования

### 1. URL versioning
Версия встроена в путь URL.

```
GET /api/v1/users
GET /api/v2/users
```

✅ Простота, видимость, кешируемость.
❌ "Загрязняет" URL — один ресурс по нескольким адресам.

### 2. Header versioning
Версия передаётся в HTTP-заголовке.

```
GET /api/users
Accept: application/vnd.myapi.v2+json
```

✅ Чистые URL, соответствует HTTP Content Negotiation.
❌ Нельзя тестировать из браузера напрямую.

### 3. Query param versioning
Версия как параметр запроса.

```
GET /api/users?version=2
```

✅ Компромисс — видно в URL, не меняет путь.
❌ Смешивается с другими параметрами.

## Deprecation policy

Когда версия устаревает, используйте стандартные заголовки (RFC 8594):

```
Deprecation: Tue, 01 Jan 2025 00:00:00 GMT
Sunset: Tue, 01 Jul 2025 00:00:00 GMT
Link: <https://api.example.com/migration>; rel="successor-version"
```
