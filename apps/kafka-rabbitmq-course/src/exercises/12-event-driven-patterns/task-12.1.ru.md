# Задание 12.1: Event Sourcing

## Цель

Реализовать визуализацию паттерна Event Sourcing для агрегата заказа. Студент должен понять ключевую идею: состояние никогда не сохраняется напрямую — оно **вычисляется** воспроизведением (replay) последовательности событий из Event Store. Компонент показывает, как ползунок управляет «точкой воспроизведения», и в реальном времени пересчитывает состояние агрегата.

## Требования

1. Определить типы событий: `OrderEventType` = `'OrderCreated' | 'ItemAdded' | 'ItemRemoved' | 'OrderPaid'`.
2. Определить интерфейс базового события `OrderEventBase` с полями `id: string`, `type: OrderEventType`, `timestamp: number`, `version: number`, и четыре конкретных интерфейса событий с типизированным `payload` для каждого типа.
3. Определить интерфейс состояния агрегата `OrderState` с полями: `orderId`, `customerId`, `items` (массив), `status: 'pending' | 'paid'`, `total: number`, `version: number`.
4. Реализовать чистую функцию `applyEvent(state: OrderState | null, event: OrderEvent): OrderState`, которая через `switch` применяет каждое событие к текущему состоянию, возвращая новое состояние (immutably).
5. Объявить массив `PRESET_EVENTS` из 5 событий: `OrderCreated` → `ItemAdded` (книга за $49, qty 1) → `ItemAdded` (книга за $54, qty 2) → `ItemRemoved` (первый товар) → `OrderPaid`. Версии 1–5.
6. Объявить словари `EVENT_COLORS` и `EVENT_ICONS` типа `Record<OrderEventType, string>` для цветовой кодировки и эмодзи-иконок каждого типа события.
7. Реализовать состояние `replayTo: number` (от 0 до `PRESET_EVENTS.length`, начальное значение = длина массива).
8. Вычислять `visibleEvents` как срез `PRESET_EVENTS.slice(0, replayTo)` и `currentState` через `visibleEvents.reduce(applyEvent, null)`.
9. Отобразить вертикальный timeline событий: каждое событие — кружок + карточка; кружок активен (цветной, с иконкой), если `idx < replayTo`, иначе серый с номером версии.
10. Отобразить блок текущего состояния агрегата: если `currentState === null` — заглушка «Состояние не инициализировано»; иначе — карточка с `orderId`, `customerId`, версией, списком позиций с количеством и ценой, итогом, бейджем статуса.
11. Отобразить `<input type="range">` от 0 до `PRESET_EVENTS.length` с подписями «Начало (пусто)» и «Воспроизведено: N/5».
12. Добавить информационный блок «Ключевой принцип» с объяснением идеи Event Sourcing.

## Чеклист

- [ ] Типы `OrderEventType`, `OrderEventBase`, конкретные события и `OrderEvent` объявлены
- [ ] Интерфейс `OrderState` содержит все 6 полей
- [ ] Функция `applyEvent` обрабатывает все 4 типа событий через `switch`
- [ ] При `ItemAdded` пересчитывается `total` через `reduce`
- [ ] При `ItemRemoved` элемент фильтруется из `items` и `total` пересчитывается
- [ ] Массив `PRESET_EVENTS` содержит ровно 5 событий с версиями 1–5
- [ ] `EVENT_COLORS` и `EVENT_ICONS` объявлены для всех 4 типов
- [ ] Ползунок корректно управляет `replayTo` и перерисовывает компонент
- [ ] `currentState` вычисляется через `reduce` из `visibleEvents`
- [ ] Timeline: активные события окрашены цветом типа, неактивные серые
- [ ] Блок состояния показывает заглушку при `replayTo === 0`
- [ ] Карточка состояния отображает позиции, итог и статус при наличии данных
- [ ] Информационный блок «Ключевой принцип» присутствует

## Как проверить себя

1. Откройте задание — ползунок установлен в максимум, все 5 событий активны, состояние показывает заказ ORD-001 со статусом «ОПЛАЧЕН» и суммой $108.
2. Перетащите ползунок в 0 — блок состояния показывает заглушку, все события серые.
3. Установите ползунок в 1 — активно только событие `OrderCreated`, состояние: пустая корзина, статус «В ОБРАБОТКЕ».
4. Установите в 3 — активны `OrderCreated` + 2x`ItemAdded`, в корзине 2 товара, итог $157.
5. Установите в 4 — `ItemRemoved` убрал первый товар, итог стал $108.
6. Установите в 5 — статус «ОПЛАЧЕН», итог $108.
7. Убедитесь, что функция `applyEvent` не мутирует входной объект — состояние всегда вычисляется заново.
