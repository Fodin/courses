# Задание 3.4: Многоуровневый кэш для новостного сайта

## Цель

Спроектировать стратегию кэширования для новостного сайта с разными типами контента: статика, API-ответы и динамический пользовательский контент. Для каждого типа выбрать уровень кэша, TTL, стратегию инвалидации и защиту от cache stampede.

## Требования

1. Создайте интерактивную таблицу проектирования с тремя строками контента:
   - **Статика** — JS/CSS/изображения
   - **API-ответы** — список статей, данные каталога
   - **Пользовательский контент** — лента пользователя, уведомления, профиль
2. Для каждого типа контента заполните столбцы:
   - **Уровни кэша** — какие использовать (Browser, CDN, Redis, DB Query Cache)
   - **TTL** — время жизни на каждом уровне
   - **Инвалидация** — стратегия (TTL, event-based, versioned keys)
   - **Stampede protection** — нужна ли защита и какая (lock, early refresh, none)
3. Покажите итоговую «карту» кэширования: какой запрос через какие уровни проходит
4. Рассчитайте примерный hit ratio для каждого уровня при заданном трафике

## Чеклист

- [ ] Три типа контента представлены в таблице
- [ ] Для каждого типа выбраны адекватные уровни кэша
- [ ] TTL логично уменьшается от статики к динамике
- [ ] Инвалидация соответствует характеру данных
- [ ] Stampede protection включена для «горячих» данных (API, популярные статьи)
- [ ] Статика кэшируется агрессивно (Browser + CDN, долгий TTL, immutable)
- [ ] Пользовательский контент — короткий TTL, event-based инвалидация
- [ ] Итоговая карта кэширования наглядна

## Как проверить себя

1. Статика: Browser Cache (max-age=1 год, immutable) + CDN — корректно?
2. API-ответы: CDN (5 мин) + Redis (1 мин) + stampede lock — корректно?
3. Пользовательский контент: только Redis (30 сек) + event-based invalidation — корректно?
4. Попробуйте изменить TTL — как это влияет на расчётный hit ratio?
5. Убедитесь, что для «горячих» API-данных включена защита от stampede
