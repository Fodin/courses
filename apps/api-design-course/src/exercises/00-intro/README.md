# Уровень 0: Введение в проектирование API

## Что такое API и зачем его проектировать

API (Application Programming Interface) — это контракт между двумя программами. Когда frontend запрашивает данные у backend, они общаются через API. Но важно не само существование API, а то, насколько хорошо оно спроектировано.

Представьте, что API — это интерфейс кофемашины. Хорошая машина: кнопка «эспрессо», кнопка «капучино», понятный экран. Плохая: один рычаг, режим зависит от того, сколько раз вы его повернули и в какую сторону. Работает? Да. Удобно? Нет.

Плохо спроектированный API — это технический долг, который платят все: frontend-разработчики тратят часы на "угадывание" поведения, тесты хрупкие, изменения ломают клиентов.

## Признаки хорошего API

| Признак | Что значит |
|---------|-----------|
| **Предсказуемость** | Зная одну часть API, угадываешь структуру другой |
| **Консистентность** | Одинаковый стиль везде: именование, форматы, ошибки |
| **Простота** | Сложность обнаруживается постепенно, не обрушивается сразу |
| **Документированность** | Актуальные примеры, описание каждого поля |
| **Правильная HTTP-семантика** | GET — безопасен, POST — создаёт, DELETE — удаляет |

## REST как доминирующий стиль

Большинство публичных API сегодня — REST (Representational State Transfer). Это не протокол и не стандарт, а архитектурный стиль поверх HTTP, предложенный Роем Филдингом в 2000 году.

Ключевые идеи REST:
- Ресурсы (существительные) в URL: `/users/42`, `/orders/5/items`
- HTTP-методы (глаголы) для действий: GET, POST, PUT, PATCH, DELETE
- Stateless — сервер не хранит состояние между запросами
- Кэшируемость — GET-запросы можно кэшировать

Richardson Maturity Model делит REST-API на 4 уровня зрелости: от Level 0 (один endpoint, всё через POST) до Level 3 (HATEOAS, самоописывающийся API). Большинство "хороших" API сегодня — Level 2.
