# Задание 12.3: Проектирование хранения сообщений

## Цель

Спроектировать data model для хранения сообщений в мессенджере: таблицы, sharding strategy, индексы, sync-протокол. Покрыть сценарии 1-to-1 чатов и групповых чатов.

## Требования

1. **Сущности** — определить таблицы: messages, chats, chat_participants
2. **Поля** — для каждой таблицы указать ключевые поля и их типы
3. **Sharding key** — выбрать и обосновать ключ шардирования для каждой таблицы
4. **Индексы** — определить индексы для основных запросов (чтение чата, список чатов, sync)
5. **Sync** — описать протокол синхронизации между устройствами

## Основные запросы, которые должна поддерживать модель

1. Получить последние N сообщений чата (пагинация)
2. Получить список чатов пользователя (отсортированный по последнему сообщению)
3. Получить новые сообщения после timestamp X (sync)
4. Получить количество непрочитанных сообщений per chat
5. Добавить сообщение в чат (1-to-1 и группа)

## Чеклист

- [ ] Таблица `messages` — messageId, chatId, senderId, content, contentType, createdAt
- [ ] Таблица `chats` — chatId, type (direct/group), name, lastMessageAt
- [ ] Таблица `chat_participants` — chatId, userId, role, joinedAt, lastReadMessageId
- [ ] Sharding по chatId для messages (все сообщения чата на одном шарде)
- [ ] Индекс (chatId, createdAt DESC) для пагинации сообщений
- [ ] Индекс (userId, lastMessageAt DESC) для списка чатов
- [ ] Sync-протокол: клиент хранит lastSyncTimestamp, запрашивает дельту
- [ ] Обоснование: почему chatId, а не userId для шардирования

## Как проверить себя

1. Пройдите по каждому из 5 основных запросов — можно ли его выполнить одним запросом к одному шарду?
2. Проверьте: что будет при добавлении нового участника в группу? Нужна ли миграция данных?
3. Проверьте: как подсчитать непрочитанные? (lastReadMessageId в chat_participants vs messageId)
4. Сравните свой дизайн с эталонным решением (Solution)
