# Задание 13.3: Проектирование социального графа

## Цель

Спроектировать хранение социального графа для системы ленты новостей: followers/following, блокировка, рекомендации. Выбрать БД, определить sharding strategy, описать основные запросы.

## Требования

1. **Сущности** — определить таблицы/коллекции: follows, blocks, user_stats
2. **Поля** — для каждой сущности указать ключевые поля и их типы
3. **Выбор БД** — обосновать выбор для каждого типа данных:
   - Graph DB для связей и рекомендаций
   - Redis для кеширования горячих данных
   - Relational DB для user stats и metadata
4. **Sharding** — выбрать ключ шардирования для таблицы follows и обосновать
5. **Основные запросы**:
   - Получить followers пользователя X
   - Получить following пользователя X
   - Проверить: подписан ли A на B
   - Mutual followers (общие подписчики A и B)
   - Рекомендации подписок (friends of friends)
6. **Hot spots** — как обрабатывать пользователей с 50M+ followers

## Чеклист

- [ ] Таблица `follows` — followerId, followeeId, createdAt
- [ ] Таблица `blocks` — blockerId, blockedId, createdAt
- [ ] Таблица `user_stats` — userId, followersCount, followingCount, postsCount
- [ ] Выбрана Graph DB (Neo4j/TAO) для графовых запросов + Redis cache
- [ ] Sharding по followeeId для быстрого получения followers
- [ ] Описаны индексы для всех основных запросов
- [ ] Решение для hot spots: chunked followers list, Redis cache
- [ ] Обоснование: почему не только Redis или только PostgreSQL

## Как проверить себя

1. Пройдите по каждому из 5 основных запросов — можно ли его выполнить эффективно?
2. Проверьте: что будет при follow/unfollow? Сколько операций?
3. Проверьте: как работает is_following(A, B)? За одну операцию?
4. Проверьте: как рекомендовать подписки? Какой traversal нужен?
5. Проверьте: селебрити с 50M followers — не создаёт ли hot spot?
6. Сравните свой дизайн с эталонным решением (Solution)
