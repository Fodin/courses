# Задание 8.2: Архитектурный конструктор — URL Shortener

## Цель

Собрать архитектуру URL Shortener из предложенных компонентов. Понять, какие блоки необходимы, как они связаны, и проверить полноту вашего решения.

## Требования

1. Вам предложен набор архитектурных компонентов (блоков)
2. Отметьте чекбоксами компоненты, которые **необходимы** для работающего URL Shortener
3. Система проверит, все ли критические компоненты выбраны
4. Для каждого выбранного компонента подумайте: **зачем он нужен** и **что сломается без него**
5. Попробуйте мысленно «пройти» оба потока: создание ссылки и redirect

## Компоненты-кандидаты

- **Client** — браузер или приложение пользователя
- **Load Balancer** — распределяет запросы между серверами
- **API Server** — обрабатывает HTTP-запросы (создание, redirect)
- **Cache (Redis)** — кэш для горячих ссылок
- **Database (SQL)** — хранит маппинг shortCode → longUrl
- **Key Generation Service** — генерирует уникальные короткие коды
- **Analytics Service** — считает клики, собирает статистику
- **CDN** — раздаёт статику (фронтенд)
- **Message Queue (Kafka)** — асинхронная обработка событий
- **Full-Text Search (Elasticsearch)** — полнотекстовый поиск

## Чеклист

- [ ] Выбраны все компоненты, необходимые для **создания** короткой ссылки
- [ ] Выбраны все компоненты, необходимые для **redirect** по короткой ссылке
- [ ] Понятно, зачем нужен Cache для read-heavy нагрузки (100:1)
- [ ] Понятно, зачем нужен Load Balancer при масштабировании
- [ ] Понятно, зачем Key Generation Service выделен в отдельный сервис
- [ ] Определены опциональные компоненты и объяснено, зачем они нужны
- [ ] Нет лишних компонентов, не относящихся к задаче

## Как проверить себя

1. Отметьте компоненты и нажмите «Проверить»
2. Система покажет, какие критические компоненты пропущены
3. Подумайте: «Если убрать этот компонент — что сломается?»
4. Для каждого опционального компонента: «Какой non-functional requirement он закрывает?»
