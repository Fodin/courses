# Callbacks: первый паттерн асинхронности

## Откуда взялись колбэки

Когда JavaScript только появился в браузерах, нужен был способ сказать движку: "сделай это позже — когда кнопка нажата, когда загрузится файл, когда пройдёт время". Решение оказалось простым — передать функцию как аргумент. Другая функция вызовет её тогда, когда результат будет готов. Эта переданная функция и есть колбэк.

```js
// Самый привычный колбэк — обработчик события
document.querySelector('button').addEventListener('click', function() {
  console.log('кнопка нажата!')
})

// setTimeout тоже принимает колбэк
setTimeout(function() {
  console.log('прошла 1 секунда')
}, 1000)
```

Колбэки бывают **синхронными** и **асинхронными**:

```js
// Синхронный — вызывается немедленно внутри функции
[1, 2, 3].forEach(n => console.log(n)) // forEach вызывает колбэк синхронно

// Асинхронный — вызывается позже, через Event Loop
setTimeout(() => console.log('позже'), 1000)
```

## Node.js и Error-First Convention

Node.js установил стандарт для асинхронных API: первый аргумент колбэка — **всегда ошибка**. Если ошибки нет — передаётся `null`. Результат — второй и последующие аргументы.

```js
const fs = require('fs')

fs.readFile('data.json', 'utf8', (err, data) => {
  if (err) {
    console.error('Не удалось прочитать файл:', err.message)
    return // важно: остановить выполнение!
  }
  console.log('Содержимое:', data)
})
```

Почему ошибка первой? Чтобы нельзя было случайно проигнорировать её — она буквально мозолит глаза. Данные `data` вообще не появляются в поле зрения, пока не проверишь `err`.

## Callback Hell: когда колбэки нанизываются друг на друга

Одиночный колбэк — удобен. Три-четыре последовательных асинхронных операции — уже боль. Каждый шаг должен начинаться внутри предыдущего, иначе порядок выполнения не гарантирован.

```js
getUser(userId, (err, user) => {
  if (err) return handleError(err)
  getPosts(user.id, (err, posts) => {
    if (err) return handleError(err)
    getComments(posts[0].id, (err, comments) => {
      if (err) return handleError(err)
      filterSpam(comments, (err, clean) => {
        if (err) return handleError(err)
        sendReport(clean, (err) => {
          if (err) return handleError(err)
          console.log('Готово!')  // наконец-то
        })
      })
    })
  })
})
```

Этот паттерн называют **Pyramid of Doom** — пирамида из закрывающих скобок растёт вправо и вниз. Код технически работает, но читать и поддерживать его становится всё тяжелее с каждым новым уровнем.

## Inversion of Control: вы теряете контроль

Самая фундаментальная проблема колбэков — не синтаксическая. Когда вы передаёте колбэк в чужую функцию, вы теряете контроль над тем:

- **Сколько раз** будет вызван ваш колбэк (один раз? три? никогда?)
- **Когда** он будет вызван (синхронно или асинхронно?)
- **С какими аргументами** он будет вызван
- **Будет ли обработана ошибка** правильно

```js
// Вы доверяете thirdPartyLib вызвать onSuccess один раз, когда надо
thirdPartyLib.processPayment(amount, {
  onSuccess: () => chargeUser(),  // а вдруг вызовет дважды?
  onError: (e) => rollback(e)
})
```

Вы буквально передаёте "продолжение своей программы" в чужие руки.

## Конкретные проблемы

**Сложная обработка ошибок.** `try/catch` не работает с асинхронными колбэками:

```js
try {
  setTimeout(() => {
    throw new Error('упс')  // этот throw НЕ поймает try/catch снаружи
  }, 1000)
} catch (e) {
  // сюда никогда не попадёт
}
```

**Невозможность вернуть значение.** Из асинхронного колбэка нельзя ничего вернуть — `return` возвращает значение из колбэка, а не из обрамляющей функции.

**Нет отмены.** Запущенный таймаут с колбэком нельзя "подождать" — можно лишь сохранить `id` и вызвать `clearTimeout`.

**Нет параллельности "из коробки".** Для двух параллельных операций нужно ручное отслеживание:

```js
let user, posts
getUser((err, u) => { user = u; if (user && posts) done(user, posts) })
getPosts((err, p) => { posts = p; if (user && posts) done(user, posts) })
```

## Частые ошибки новичков

**Ошибка 1: Забытый `return` после проверки ошибки**

```js
// Плохо — без return продолжит выполнение!
readFile((err, data) => {
  if (err) console.error(err)  // ошибку залогировали
  processData(data)             // а data = undefined, краш!
})

// Хорошо
readFile((err, data) => {
  if (err) { console.error(err); return }
  processData(data)
})
```

**Ошибка 2: Синхронный и асинхронный колбэк одновременно (Zalgo)**

```js
// Плохо — иногда синхронный, иногда нет — непредсказуемо
function getCache(key, cb) {
  if (cache[key]) cb(cache[key])          // синхронно!
  else fetch(url).then(data => cb(data))  // асинхронно!
}

// Хорошо — всегда асинхронный
function getCache(key, cb) {
  if (cache[key]) return setTimeout(() => cb(cache[key]), 0)
  fetch(url).then(data => cb(data))
}
```

**Ошибка 3: Забытая обработка ошибки**

```js
// Плохо — ошибка "проглочена"
asyncOp((err, result) => {
  doSomething(result)  // если err !== null, result = undefined
})

// Хорошо — всегда проверяй err первым
asyncOp((err, result) => {
  if (err) return handleError(err)
  doSomething(result)
})
```

## Ключевые выводы

- Колбэки — исторически первый паттерн асинхронности в JS
- Error-first `(err, data)` — стандарт Node.js, предотвращает случайное игнорирование ошибок
- Callback Hell возникает при последовательных асинхронных операциях
- Inversion of Control — потеря контроля над вызовом своего кода
- Promise решает эти проблемы, возвращая контроль — следующая тема
