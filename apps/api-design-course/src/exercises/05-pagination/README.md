# Пагинация и фильтрация

## Зачем нужна пагинация

Возвращать все 10 миллионов записей из базы в одном ответе — плохая идея. Пагинация делит большой набор данных на страницы: сервер отдаёт только часть, клиент запрашивает следующую по мере необходимости.

Без пагинации API становится нестабильным при росте данных: таймауты, перегрузка памяти, медленный клиент.

## Offset vs Cursor: ключевые различия

| Критерий | Offset (page/limit) | Cursor (after/first) |
|----------|---------------------|----------------------|
| Переход на страницу N | ✅ Да | ❌ Только последовательно |
| Общий счётчик | ✅ totalCount | ⚠️ Сложно |
| Стабильность при вставках | ❌ Дубли/пропуски | ✅ Стабильно |
| Производительность | ❌ OFFSET деградирует | ✅ Быстро |
| Применение | Админ-панели | Ленты, бесконечный скролл |

**Offset**: `GET /api/posts?page=3&limit=20` или `?offset=40&limit=20`

**Cursor**: `GET /api/posts?after=cursor_abc&first=20`

## Query-параметры для фильтрации и сортировки

```
GET /api/products
  ?status=active          # простой фильтр
  &price[gte]=100         # оператор (>=)
  &price[lte]=5000        # оператор (<=)
  &sort=-createdAt        # сортировка: минус = DESC
  &page=2&limit=20        # пагинация
```

Сортировка с минусом (`-name`) — конвенция GitHub API. Несколько полей: `sort=status,-createdAt`.

## Мета-данные в ответе

```json
{
  "data": [...],
  "meta": {
    "totalCount": 247,
    "page": 2,
    "limit": 20,
    "totalPages": 13,
    "hasNextPage": true,
    "hasPrevPage": true
  }
}
```

Для cursor-пагинации вместо `page`/`totalPages` используют `pageInfo`:

```json
{
  "pageInfo": {
    "hasNextPage": true,
    "endCursor": "cursor_xyz",
    "startCursor": "cursor_abc"
  }
}
```
