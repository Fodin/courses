# Уровень 15: pnpm — устройство и отличия

## Что такое pnpm

pnpm (performant npm) — альтернативный пакетный менеджер для Node.js, совместимый с npm-реестром. Главная идея: хранить каждый пакет в глобальном хранилище ровно один раз и подключать его в проекты через жёсткие ссылки (hard links).

## Глобальное content-addressable хранилище

Все скачанные пакеты хранятся в `~/.local/share/pnpm/store` (Linux/macOS) или `%LOCALAPPDATA%/pnpm/store` (Windows). Это **content-addressable store**: каждый файл идентифицируется по хешу своего содержимого, а не по имени.

```
~/.local/share/pnpm/store/v3/
  files/
    00/abc123...   ← файл пакета, идентифицирован по содержимому
    01/def456...
    ...
```

При установке одного и того же пакета в несколько проектов файлы не копируются — создаются **hard links**. На диске данные физически одни, но к ним ведут несколько ссылок.

## Структура node_modules у pnpm

npm создаёт плоский node_modules, где все транзитивные зависимости поднимаются в корень. pnpm делает иначе:

```
node_modules/
  .pnpm/                          ← виртуальный store
    express@4.18.2/
      node_modules/
        express/   ← hard link → ~/.pnpm-store
        accepts/   ← hard link → ~/.pnpm-store
  express/         ← симлинк → .pnpm/express@4.18.2/node_modules/express
```

В корне `node_modules` — только симлинки на **прямые** зависимости проекта. Транзитивные зависимости живут внутри `.pnpm/` и не видны из корня.

## Строгая изоляция: нет фантомных зависимостей

**Фантомная зависимость** — импорт пакета, которого нет в `package.json`, но который попал в `node_modules` через подъём транзитивной зависимости.

У npm это работает случайно: если `express` тянет `debug`, то `require('debug')` в вашем коде тоже работает. Но это не задекларировано, и при обновлении express версия debug может измениться или пакет исчезнет.

pnpm такое **не допускает**: симлинк на `debug` в корне отсутствует, и `require('debug')` из вашего кода упадёт с ошибкой MODULE_NOT_FOUND, если debug не указан в package.json.

## Файл блокировки pnpm-lock.yaml

pnpm использует `pnpm-lock.yaml` вместо `package-lock.json`. Формат включает поле `packages` с информацией о каждом пакете, его зависимостях и хеше для проверки целостности.

## Основные команды

```bash
pnpm install          # установка зависимостей
pnpm add express      # добавить пакет
pnpm add -D typescript  # добавить в devDependencies
pnpm remove express   # удалить пакет
pnpm update           # обновить зависимости
pnpm run build        # запустить скрипт
pnpm dlx create-react-app my-app  # аналог npx (без установки в проект)
```

## Поле pnpm.overrides

Для принудительной замены версии транзитивной зависимости в `package.json`:

```json
{
  "pnpm": {
    "overrides": {
      "lodash": "4.17.21",
      "express>debug": "4.3.4"
    }
  }
}
```

## ⚠️ Частые ошибки

❌ Запуск проекта, мигрировавшего с npm, без очистки `node_modules` — плоская структура npm и симлинк-структура pnpm конфликтуют.

✅ Всегда удалять `node_modules` и старый lockfile перед `pnpm install`.

❌ Ожидать, что код, импортирующий фантомную зависимость, будет работать с pnpm.

✅ Добавить все реально используемые пакеты в `package.json`.

## Скорость установки

pnpm быстрее npm и yarn classic за счёт параллельных загрузок и отсутствия копирования файлов (hard links вместо копий). При повторных установках большинство файлов уже есть в global store — создаются только ссылки.
