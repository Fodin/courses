# Задание 7.4: Async Mutex

## Цель

Реализовать класс `AsyncMutex` для защиты общего состояния от race condition при конкурентных async-операциях. Продемонстрировать разницу: без mutex счётчик после 10 операций двух процессов не равен 20, с mutex — ровно 20.

## Требования

1. **Класс `AsyncMutex`** с методами:
   - `acquire(): Promise<void>` — захватывает блокировку (ждёт если занята)
   - `release(): void` — освобождает блокировку, передаёт следующему в очереди
   - `withLock<T>(fn: () => Promise<T>): Promise<T>` — удобная обёртка

2. **Симуляция двух процессов** A и B, каждый выполняет 5 итераций:
   - Читает `counter`
   - Ждёт случайную задержку 20-50ms
   - Пишет `counter + 1`

3. **Переключатель Mutex ON/OFF** — видеть разницу поведения без смены кода

4. **Лог операций** в реальном времени: процесс, действие (read/write), текущее значение счётчика, отметка конфликта (красная подсветка)

5. **Итоговое сообщение**: фактическое значение счётчика vs ожидаемые 10

## Чеклист

- [ ] Компонент называется `Task7_4` и экспортируется по умолчанию
- [ ] `useLanguage` импортирован и `t('task.7.4')` используется в заголовке
- [ ] `AsyncMutex` реализован через Promise + queue (не через setTimeout)
- [ ] Без mutex: финальный счётчик почти всегда < 10 из-за race condition
- [ ] С mutex: финальный счётчик всегда = 10
- [ ] В логе видно чередование A и B с временными метками
- [ ] Конфликты (lost update) подсвечены красным цветом
- [ ] Нет TypeScript-ошибок типа `any`

## Как проверить себя

1. Переключатель OFF (без mutex): запустите несколько раз — счётчик будет 4-9 (редко 10)
2. Переключатель ON (с mutex): запустите 5 раз — счётчик всегда ровно 10
3. В логе без mutex: найдите строки "КОНФЛИКТ!" — их наличие объясняет потерю обновлений
4. В логе с mutex: A и B никогда не выполняют read одновременно, операции строго чередуются
