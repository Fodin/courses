# Пагинация и фильтрация

## Зачем нужна пагинация

Возвращать все 10 миллионов записей из базы в одном ответе — плохая идея. Пагинация делит большой набор данных на страницы: сервер отдаёт только часть, клиент запрашивает следующую по мере необходимости.

Без пагинации API становится нестабильным при росте данных: таймауты, перегрузка памяти, медленный клиент.

## Offset vs Cursor: ключевые различия

| Критерий | Offset (page/limit) | Cursor (after/first) |
|----------|---------------------|----------------------|
| Переход на страницу N | ✅ Да | ❌ Только последовательно |
| Общий счётчик | ✅ totalCount | ⚠️ Сложно |
| Стабильность при вставках | ❌ Дубли/пропуски | ✅ Стабильно |
| Производительность | ❌ OFFSET деградирует | ✅ Быстро |
| Применение | Админ-панели | Ленты, бесконечный скролл |

**Offset**: `GET /api/posts?page=3&limit=20` или `?offset=40&limit=20`

**Cursor**: `GET /api/posts?after=cursor_abc&first=20`

## Query-параметры для фильтрации и сортировки

```
GET /api/products
  ?status=active          # простой фильтр
  &price[gte]=100         # оператор (>=)
  &price[lte]=5000        # оператор (<=)
  &sort=-createdAt        # сортировка: минус = DESC
  &page=2&limit=20        # пагинация
```

Сортировка с минусом (`-name`) — конвенция GitHub API. Несколько полей: `sort=status,-createdAt`.

## Мета-данные в ответе

```json
{
  "data": [...],
  "meta": {
    "totalCount": 247,
    "page": 2,
    "limit": 20,
    "totalPages": 13,
    "hasNextPage": true,
    "hasPrevPage": true
  }
}
```

Для cursor-пагинации вместо `page`/`totalPages` используют `pageInfo`:

```json
{
  "pageInfo": {
    "hasNextPage": true,
    "endCursor": "cursor_xyz",
    "startCursor": "cursor_abc"
  }
}
```

## Field filtering — борьба с over-fetching

Пагинация ограничивает число **строк**, а field filtering — число **полей** в каждой строке. Это две разные оси экономии трафика.

**Over-fetching** — клиенту нужны `id` и `name`, а API отдаёт весь объект с 30 полями. Списку из 100 товаров это раздувает ответ в разы.

Решение — параметр `fields` (sparse fieldsets, конвенция JSON:API):

```
GET /products?fields=id,name,price     # вернуть только эти поля
GET /users/42?fields=id,email          # частичное представление
```

```json
// GET /products?fields=id,name → компактный ответ
{ "data": [ { "id": 1, "name": "Кофе" }, { "id": 2, "name": "Чай" } ] }
```

Это «бедный человек» GraphQL: клиент сам решает, что ему нужно. Правило: `fields` уменьшает только набор полей, но не меняет структуру ресурса.

## Сжатие ответа (gzip)

Даже компактный JSON хорошо сжимается — текст избыточен. Клиент сообщает, что умеет распаковывать, сервер сжимает:

```http
# Запрос
Accept-Encoding: gzip, br

# Ответ
Content-Encoding: gzip
```

Gzip уменьшает JSON-ответ обычно на 70–90%. Это **бесплатная** оптимизация на уровне инфраструктуры (nginx, CDN), почти всегда включённая по умолчанию. Trade-off: лишняя нагрузка на CPU, поэтому крошечные ответы (несколько сотен байт) сжимать смысла нет.

**Три оси экономии трафика** работают вместе: пагинация режет строки, `fields` режет поля, gzip сжимает остаток.
