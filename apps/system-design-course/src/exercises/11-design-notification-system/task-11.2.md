# Задание 11.2: Конструктор Notification Pipeline

## Цель

Собрать notification pipeline из предложенных этапов в правильном порядке. Понять, почему каждый этап стоит именно на своём месте, и увидеть, как событие проходит через весь pipeline с фильтрацией на каждом шаге.

## Требования

1. Вам предложен набор этапов notification pipeline (в случайном порядке)
2. Расставьте этапы в правильном порядке перетаскиванием (drag-and-drop)
3. Нажмите «Проверить» — система покажет, какие этапы стоят правильно
4. После сборки правильного pipeline — запустите симуляцию прохождения события
5. Наблюдайте, как событие фильтруется на каждом этапе (dedup отсекает дубли, preference убирает отключённые каналы и т.д.)

## Этапы pipeline

- **Event Trigger** — внешний сервис генерирует событие (заказ, OTP, промо)
- **Deduplication** — проверка idempotency key, отсечение дублей
- **Preference Check** — проверка каналов пользователя, тихих часов, отписок
- **Template Render** — подстановка переменных в шаблон сообщения
- **Priority Queue** — постановка в очередь по приоритету (critical/high/normal/low)
- **Channel Router** — маршрутизация в конкретный канал (push/email/SMS/in-app)
- **Delivery** — отправка через провайдера (APNs, SendGrid, Twilio)

## Чеклист

- [ ] Все 7 этапов расставлены в правильном порядке
- [ ] Понятно, почему dedup стоит перед preference check (экономия ресурсов)
- [ ] Понятно, почему template render до очереди (в очередь попадает готовое сообщение)
- [ ] Понятно, почему priority queue до channel router (приоритет определяет порядок обработки)
- [ ] Запущена симуляция и прослежен путь хотя бы 3 разных событий
- [ ] Понятно, на каких этапах событие может быть отфильтровано и почему

## Как проверить себя

1. Расставьте этапы и нажмите «Проверить»
2. Если есть ошибки — подумайте: «Что будет, если поменять местами эти два этапа?»
3. Запустите симуляцию для разных типов событий (OTP, промо, social)
4. Проследите, как деdup отсекает повторное событие, а preference check фильтрует отключённый канал
