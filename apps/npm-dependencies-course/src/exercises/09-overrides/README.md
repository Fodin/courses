# Уровень 9: overrides — принудительная замена транзитивных зависимостей

## Зачем нужен overrides

Вы зависите от пакета A, который зависит от пакета B версии 1.0.0. В B найдена уязвимость, но автор A ещё не выпустил обновление. Обычный `npm install` установит уязвимую B@1.0.0 — вы не можете это изменить через свой `package.json`.

**overrides** — механизм npm (v8.3+), позволяющий принудительно задать версию любого пакета в дереве зависимостей, включая транзитивные.

## Базовый синтаксис

```json
{
  "overrides": {
    "lodash": "4.17.21"
  }
}
```

Это заменяет **все** вхождения `lodash` в дереве на `4.17.21` — независимо от того, кто её требует.

## Вложенный (scoped) override

Заменить версию только когда пакет является зависимостью конкретного родителя:

```json
{
  "overrides": {
    "some-package": {
      "lodash": "4.17.21"
    }
  }
}
```

Здесь `lodash` будет принудительно установлен в `4.17.21` только внутри зависимостей `some-package`. В остальных местах дерева lodash остаётся прежним.

## Ключ "." — замена самого пакета

Внутри вложенного override ключ `"."` означает версию целевого пакета:

```json
{
  "overrides": {
    "some-package": {
      ".": "2.0.0",
      "lodash": "4.17.21"
    }
  }
}
```

Здесь `some-package` сам будет принудительно заменён на `2.0.0`, а `lodash` внутри него — на `4.17.21`.

## Ссылка на прямую зависимость через $

Префикс `$` позволяет сослаться на версию, уже указанную в `dependencies` или `devDependencies`:

```json
{
  "dependencies": {
    "react": "^18.2.0"
  },
  "overrides": {
    "react": "$react"
  }
}
```

Означает: «все вхождения react в дереве — использовать ту же версию, что указана в моих dependencies». Полезно для обеспечения единственности экземпляра React.

## Ограничения overrides

- Работают **только из корневого** `package.json`. Если `overrides` объявлены в зависимости — они игнорируются npm.
- Влияют на **всё дерево** проекта.
- Могут конфликтовать с объявленными диапазонами версий (пакет может получить версию, которую он не ожидал).
- Появились в **npm v8.3** (январь 2022). В более старых npm не поддерживаются.

## Сравнение с аналогами

| Менеджер         | Поле             | Синтаксис                                      |
| ---------------- | ---------------- | ---------------------------------------------- |
| npm v8.3+        | `overrides`      | `{ "pkg": "version" }`                         |
| yarn v1          | `resolutions`    | `{ "pkg": "version" }`, поддерживает glob-пути |
| yarn v2+ (berry) | `resolutions`    | Аналогично, но через `packageExtensions`       |
| pnpm             | `pnpm.overrides` | `{ "pkg": "version" }` — в корне package.json  |

Семантика похожа, но синтаксис вложенных путей отличается: yarn `resolutions` поддерживает glob-нотацию `"pkg/dep": "version"`, pnpm `pnpm.overrides` — аналог npm overrides.

## Когда использовать overrides

✅ Фиксация уязвимости в транзитивной зависимости, когда maintainer ещё не выпустил патч  
✅ Обеспечение единственного экземпляра React/других singleton-библиотек  
✅ Временный откат транзитивной зависимости при регрессии  
❌ Вместо обновления прямой зависимости — обновите её, это чище  
❌ Как постоянное решение — overrides — временный костыль до выхода патча

## ⚠️ Типичные ошибки

❌ Объявлять overrides в package.json библиотеки в расчёте на потребителей  
✅ Overrides работают только из корневого package.json приложения

❌ Устанавливать через override версию, несовместимую с API ожидающего пакета  
✅ Проверять, что принудительная версия фактически совместима с потребителем
